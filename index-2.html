The Goal

What We're Building & Why

Every ACO that exists right now is Discord-only. That works fine for personal use, but it's a real limitation for anyone trying to run this as a business — because it means every customer has to be in your server, learn the bot, and stay inside Discord to place an order. That's friction you don't need.

Two things are driving this build. First, the Discord bot needs to be as good as what's already out there — same ease of use, same speed, same command UX that people are used to. Second, and this is the part nobody else has done yet: a secure API that any website can plug into, so customers on a reseller's site never have to touch Discord at all.

Discord — match the best

The bot has to feel familiar on day one

People using the current ACOs are comfortable with them. Slash commands, clean embeds, live status updates, DMs when something needs attention. We're matching all of that and building on top of it — not asking anyone to learn something new from scratch.

The API — what nobody else has

Resellers can build their own storefront

A reseller integrates the API once. Their customers order through the reseller's website. The platform handles checkout in the background. Customer never needs Discord. Reseller gets full control over their own experience. This is what changes the business model.

What We Can Build

Discord Bot + Secure API

Both run off the same backend. They can share a VPS or sit on separate servers — separate is slightly faster under heavy API load, but for most setups shared is simpler and works fine. Either way, adding one doesn't complicate the other.

Discord bot

Slash commands throughout — no text syntax to memorise. Selection menus, confirmation prompts, live status embeds that update as a checkout runs. If you're comfortable with the bots you're currently using, this will feel familiar from the first session.

  • /checkout — start a task, choose retailer, profile, items from menus
  • /status — live state of an active task, updates in-embed
  • /cancel — cancel a queued or in-progress task
  • /profiles — create, list, switch profiles
  • /cards — add, remove, view cards (masked)
  • /proxies — add, bulk-add, view health, remove
  • /orders — order history with retailer, total, status

Discord DM notifications fire automatically when: a CAPTCHA requires the user's attention, a payment is declined, an order is confirmed or fails. The user is never left wondering what happened.

The API

Everything in the Discord bot is also available through the API. A reseller integrates it once — their customers order through whatever website they build, the API handles checkout in the background, and there's no Discord involved on the customer's side at all. API key auth, configurable scopes, per-key rate limits, and webhooks for every event.

How a reseller's website uses the API
Customer places order on reseller's site → Reseller site calls POST /v1/tasks
Platform runs checkout in background → Webhook fires: order.confirmed
Reseller site receives webhook → Customer sees "Order placed" — done

Instacart — Including Promotional Account Support

Instacart is the most technically involved integration in the scope. You're right that it's possible — a small number of existing tools do it — and you're also right that the promotional account path (using credits or promo balances instead of or alongside a card) is key to making it work efficiently for your use case. Here's how we approach it.

The promotional account path

Instacart accounts that carry promotional credit or a pre-loaded balance have a different checkout path than standard card accounts. Instead of — or in addition to — entering a card, the checkout applies the available credit first, then handles any remaining balance. The platform detects which payment path the account is showing and handles each one automatically:

Instacart payment path detection
Reach payment step → Detect which UI is shown
Credit covers full amount → No card needed — submit directly
Partial credit + card needed → Apply credit → enter card for remainder
No credit — standard card → Normal card cycling path

To build this correctly, we need to walk through the flow on the specific account type you'll be using. The structure is built and ready — the exact UI selectors and payment logic are confirmed during the discovery session with you before implementation begins.

What we need from you before the Instacart build starts

  • Confirmation of whether the account is standard, Instacart+, or a business account
  • A walkthrough of a sample order so we can see the exact payment screen the account shows
  • Your preference on store selection — specific stores, or best-match for the delivery address?
Instacart discovery is scheduled last for a reason Everything else in the platform can be built and running while the Instacart discovery session is being arranged. The discovery session is not a blocker for the rest of the project — it's a prerequisite for that specific module only.
What We Can Build

Advanced Capabilities Built Into the Core

These aren't features that get added later — they're baked into the engine design from the start. You asked about them specifically and they're confirmed scope.

CAPTCHA & Verification

Auto-solve with user fallback

The engine detects CAPTCHA challenges and attempts to solve them automatically using 2Captcha and CapSolver. If automation fails, the checkout pauses and the user gets a Discord DM with a link to resolve it manually. Once resolved, checkout resumes from exactly where it stopped. The same mechanism handles 3DS payment verification.

Anti-Detection

Browser session management

Every checkout runs in an isolated browser session with a consistent fingerprint — realistic canvas rendering, WebGL signals, screen dimensions, user agent, timezone, and behaviour patterns. Sessions are health-checked throughout the checkout; a session that shows signs of detection is automatically recreated before continuing.

Rate Limiting

Automatic backoff and recovery

When a retailer rate-limits a request, the platform classifies it correctly, puts the retailer into a cooldown window (all workers are aware), requeues the task with exponential backoff, and resumes automatically when the window clears. The user doesn't need to do anything. Rate limits are not failures — they're managed states.

Full Audit Trail

Every event recorded

Every state transition across every checkout task is recorded — CAPTCHA detected, CAPTCHA solved, payment declined, card cycled, order confirmed, and so on. This makes troubleshooting straightforward and gives you a clear picture of where any given order stands or why it failed.

What We Can't Promise

What We Can't Promise

Most project documents skip this part. We're not going to, because finding out later is worse than knowing now.

Retailer sites change

A checkout flow that works today can break tomorrow

Any of these retailers can push a site update that moves a button, changes a field, or adds a new verification step. When that happens, the integration for that retailer stops working until it's fixed. That's just the reality of automating against sites you don't control.

The monitoring catches it fast — a failure rate spike per retailer is visible within minutes, not days. Each retailer is its own self-contained module so the fix is scoped. The question is always how significant the change was: a selector tweak is an hour, a full flow overhaul takes longer.

Bot detection evolves

Stealth config works at launch — some retailers will update theirs

Every integration gets tuned against the retailer's detection before it goes live. That holds until the retailer updates their detection — which some do on a schedule, and others do reactively based on traffic patterns. We can't know when or how significant it'll be until it happens.

Nightly regression tests catch it the morning after, not from user reports. The fix is per-retailer — nothing else gets touched. But this is ongoing work, not a one-time setup. Anyone who tells you otherwise isn't being straight with you.

CAPTCHA auto-solve has limits

The common types get handled automatically — not all of them, every time

reCAPTCHA, hCaptcha, Turnstile — solved automatically most of the time via 2Captcha and CapSolver. But harder difficulty settings or newer challenge types can beat the solver. When that happens, the checkout pauses and the user gets a DM to handle it manually. It takes a couple of minutes and checkout picks back up automatically once they confirm.

Solve rates are tracked per retailer. If something starts failing at a higher rate, it shows in the data and gets addressed. We're not going to say it's always automatic, because it isn't.

Uber Eats is the most complex one

Other ACOs do it — but it needs the most ongoing attention after launch

Uber Eats needs a logged-in account, handles location-based store availability, has its own detection layer, and adds tip and fee logic on top of standard checkout. It's doable — the competition does it — but it's the integration most likely to need patches post-launch. It gets built last, after the stealth and session infrastructure is already proven on the direct retailers, which helps. Conservative concurrency limits on Uber Eats specifically reduce the detection surface.

Instacart's promo flow needs your account to confirm

We've built the structure — the exact logic depends on what your account shows

Instacart's payment step looks different depending on account type, membership status, and active promotions. The adapter is built to detect which path it's on at runtime and handle it — but we need to walk through your specific account before we can wire in the right selectors and confirm the flow. That's what the discovery session is for. Everything else can be running while we arrange it.

Day-to-Day Reality

Quick-Fix Playbook

For the most common issues — how fast each gets resolved and what the path is.

Fix time: minutes

Selector breaks for one retailer

Each retailer's selectors live in a single selectors.ts file for that retailer module. Update the selector, push the change, the worker picks it up on next restart. No other retailers are touched. This is the most common maintenance task and intentionally designed to be fast.

Fix time: automatic

Rate limit or temporary block

Fully automatic. The error classifier identifies the rate limit, sets a cooldown key in Redis, requeues the task with the appropriate delay. When the cooldown expires, the task runs again. Zero human intervention required unless the rate limit is sustained for an unusually long time.

Fix time: user action

CAPTCHA that auto-solve can't handle

User receives a Discord DM with a link to the task in the dashboard. They open the page, the CAPTCHA is shown, they solve it manually in the browser, click "Done" — the checkout resumes automatically from that point. Total user time: typically under two minutes.

Fix time: automatic

Card declined

Engine moves to the next card in the profile without stopping. User gets a Discord DM notification that a card was declined and which one (by last 4 digits) so they know which card to replace. If all cards are exhausted, the task fails and the user is notified with the specific reason.

Fix time: hours to a day

Retailer bot detection update

Grafana alerts on increased block rate for the affected retailer. Developer reviews the detection pattern, updates fingerprint config or session behaviour for that retailer specifically. Nightly regression test validates the fix before it's pushed to production.

Fix time: automatic

Worker process crashes

The supervisor process automatically detects a crashed worker and spawns a replacement. In-progress tasks that were interrupted are requeued. Average downtime per worker crash: under 2 seconds. This is by design — individual worker crashes don't affect the queue or other workers.

Day-to-Day Reality

How Issues Get Caught

The platform doesn't wait for users to report problems. Everything is monitored and most issues surface automatically before they affect more than a handful of tasks.

Real-time Grafana dashboard shows
  • Checkout success / failure rate per retailer
  • Queue depth — how many tasks are waiting
  • Active worker count and health
  • Rate-limit events per retailer per minute
  • CAPTCHA solve success rate by type
  • Proxy health ratio per tenant
  • Memory usage per worker (auto-restart at threshold)
  • Webhook delivery success rate
Automatic alerts fire when
  • Failure rate for any retailer exceeds 20% over 10 minutes
  • Any retailer's rate-limit events spike above threshold
  • Queue depth for any retailer grows unusually large
  • All proxies for a tenant become unhealthy
  • Any worker's memory exceeds 400 MB
  • Nightly regression test fails for a retailer
  • Webhook delivery failure rate rises above 50%
Every retailer runs a full automated checkout test every night against a real test account. If an integration broke overnight, it shows up in the morning before any real users hit it. That nightly test is probably the most useful single thing in the whole platform from an ops standpoint — it catches the majority of breakages before they matter.
